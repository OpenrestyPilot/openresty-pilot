# ORP 配置管理平台 PRD

## Problem Statement

企业需要统一管理多个 OpenResty/Nginx 中心和节点实例的 HTTP、Stream、Upstream、Server、Location、TLS、DNS、策略及发布流程。当前运维人员面临以下问题：

- 配置分散在节点文件中，难以确认哪个配置属于哪个中心和节点。
- HTTP 块、Server 块、Location 的配置层级不够直观，继承关系容易被误解。
- 4xx/5xx 错误页面只能进行有限的默认页面配置，无法按状态码、作用域和请求 Content-Type 提供不同内容。
- 错误页面编辑界面一次展示全部页面，页面较长，编辑目标不聚焦，也不便于增加自定义状态码。
- 安全响应头、日志格式、错误页面等配置保存后，还需要经过原生配置渲染、发布和 reload 才能真正生效。
- 节点实例需要自行向控制面声明身份，避免依赖独立的 Compose 注册服务。
- 多节点发布、reload 结果、活动版本和审计证据需要在一个控制面中闭环追踪。

## Solution

建设一个以中心（Center）为发布边界的 OpenResty 配置管理平台：

- 使用 Go 控制面统一提供已迁移资源的结构化配置和审计查询；未迁移的发布与运行时能力在完成 Go 实现前不可用。
- 使用管理 Web 提供中心、节点实例、HTTP/Stream 资源、策略和发布操作。
- 使用 MySQL 作为配置权威来源，Redis 仅作为可选基础设施。
- 将配置渲染为可预览、可校验、可物化的原生 Nginx 配置制品。
- 通过 Control API 对节点实例执行 reload，并记录逐节点结果。
- 将 HTTP 错误页面设计为“作用域 + 状态码 + Content-Type”维度：HTTP 块提供全局默认，Server 块可覆盖；优先匹配具体 Content-Type，未匹配时回退到状态码默认页面。
- 节点启动后通过 REST 接口主动登记自身，登记身份必须由节点环境变量显式配置。

## User Stories

1. 作为平台管理员，我希望创建和管理多个配置中心，以便隔离不同业务环境的配置发布边界。
2. 作为平台管理员，我希望在中心下登记节点实例，以便统一查看节点地址、协议、Control API 和启用状态。
3. 作为平台管理员，我希望删除节点实例后重启系统不会自动恢复它，以便数据库中的节点状态与我的操作保持一致。
4. 作为平台管理员，我希望节点实例在启动后按显式配置主动登记自身，以便测试环境不需要独立注册服务。
5. 作为运维人员，我希望查看中心内所有 HTTP 节点实例，以便快速定位配置目标。
6. 作为运维人员，我希望配置 HTTP 块的 root、default_type、缓冲区、keepalive、gzip 和文件传输参数，以便统一管理全局 HTTP 行为。
7. 作为运维人员，我希望配置 HTTP 和 Stream 日志格式，以便统一收集访问日志和四层会话日志。
8. 作为安全管理员，我希望启用或关闭预制安全响应头，以便快速应用常见安全基线。
9. 作为安全管理员，我希望新增自定义响应头，以便满足业务安全策略和合规要求。
10. 作为运维人员，我希望配置 HTTP 块级别的默认错误页面，以便所有 Server 可以继承统一行为。
11. 作为运维人员，我希望在 Server 块中覆盖特定错误页面，以便不同站点返回不同品牌或业务提示。
12. 作为运维人员，我希望支持 4xx 错误页面，以便处理客户端请求错误、认证失败、权限不足和资源不存在等场景。
13. 作为运维人员，我希望支持 5xx 错误页面，以便处理网关、上游和服务不可用等场景。
14. 作为运维人员，我希望通过状态码选择器一次只编辑一个错误页面，以便在大量状态码中保持编辑界面清晰。
15. 作为运维人员，我希望新增自定义的 100–599 HTTP 状态码错误页面，以便支持非预置状态码和业务扩展状态码。
16. 作为 API 管理员，我希望针对同一个状态码配置 HTML、JSON 或纯文本页面，以便浏览器、API 客户端和命令行客户端获得合适的响应格式。
17. 作为 API 管理员，我希望系统优先匹配请求 Content-Type 对应的错误页面，未匹配时回退到该状态码的默认页面，以便配置具有确定的降级行为。
18. 作为运维人员，我希望错误页面支持 `application/json`、`text/html`、`text/plain` 以及带参数的 Content-Type，以便兼容常见客户端请求头。
19. 作为运维人员，我希望系统拒绝非法状态码、非法 Content-Type、超大页面内容和危险路径内容，以便避免生成不可用或不安全的原生配置。
20. 作为运维人员，我希望预览渲染后的 nginx.conf 和 include 文件，以便在发布前确认 error_page、map、alias 和继承结果。
21. 作为运维人员，我希望保存操作只更新配置草稿而不立即影响节点，以便在发布前集中检查多项变更。
22. 作为发布人员，我希望发布过程先生成运行时快照，再原子物化原生配置，最后调用节点 Control API reload，以便发布过程可追踪且不会产生半成品目录。
23. 作为发布人员，我希望看到每个节点的 reload 成功、失败或未知状态，以便判断发布是否真正完成。
24. 作为发布人员，我希望发布失败时能看到明确的校验或节点错误信息，以便快速修复配置。
25. 作为审计人员，我希望所有中心、节点、配置和发布写操作都有审计记录，以便追踪变更来源和时间。
26. 作为运维人员，我希望查看活动版本而不是仅查看数据库草稿，以便确认节点当前实际运行的配置制品。
27. 作为运维人员，我希望支持配置版本差异和回滚，以便在错误页面或安全配置导致异常时恢复到已验证版本。
28. 作为运维人员，我希望管理 HTTP Upstream 及其 Target，以便配置代理目标和健康检查。
29. 作为运维人员，我希望管理 HTTP Server 和 Location，以便配置域名、监听端口、TLS、代理、静态文件和直接返回规则。
30. 作为运维人员，我希望管理 Stream TCP/UDP 服务，以便统一维护四层流量配置。
31. 作为安全管理员，我希望将 IP、API 和限速策略独立启停并绑定到明确资源，以便策略默认关闭且不会误作用于未绑定资源。
32. 作为证书管理员，我希望管理 TLS 证书并在 Server 中选择已启用证书，以便 HTTPS 配置具备明确的证书来源。
33. 作为平台管理员，我希望 Redis 不可用时基础配置仍以 MySQL 为准并可继续管理，以便可选基础设施故障不会阻断配置管理。
34. 作为运维人员，我希望查看节点访问日志和错误日志，并能区分来源节点和日志类型，以便进行故障排查。
35. 作为运维人员，我希望发布后通过日志流和健康状态验证节点行为，以便区分“配置已生成”和“运行时已生效”。
36. 作为前端用户，我希望 HTTP 配置页面在日志格式、安全响应头、自定义响应头之间保持清晰间距和一致布局，以便减少误操作。
37. 作为前端用户，我希望错误页面编辑界面只显示当前选中的页面内容，同时保留新增和切换入口，以便高效维护页面。
38. 作为平台管理员，我希望 Swagger/OpenAPI 能反映新增的错误页面字段和节点行为，以便其他系统可以正确集成。

## Implementation Decisions

- 采用中心（Center）作为配置和发布边界，节点实例归属于中心。
- 使用 MySQL 持久化中心配置、节点实例、HTTP/Stream 资源、策略、配置版本、发布结果和审计记录；Redis 不作为配置权威。
- Go 控制面使用显式 SQL、UUID 二进制转换和 JSON DTO，REST 路径及字段保持兼容。
- 所有数组和结构化配置使用 JSON 列，并由 Go 控制面统一序列化。
- 所有 schema 变更必须提供可重复执行的迁移脚本，并在本地 MySQL 实例验证。
- HTTP 错误页面采用 JSON 映射保存，支持两类键：
  - `状态码`：该状态码的默认页面。
  - `状态码|Content-Type`：该状态码在指定请求 Content-Type 下的专用页面。
- 错误页面匹配使用请求头 `$http_content_type`。匹配优先级为具体 Content-Type 页面、状态码默认页面、OpenResty 默认行为。
- Content-Type 匹配需要允许媒体类型参数，例如 `application/json; charset=utf-8`，但禁止换行、路径穿越和非法字符。
- 错误页面页面内容限制为 1MB，并生成到受控的错误页面目录；文件名由状态码和经过安全化处理的 Content-Type 组成。
- HTTP 块的错误页配置生成全局 `map`；Server 块继承 HTTP 块配置，并允许对状态码和 Content-Type 进行覆盖。
- 原生配置渲染必须同时生成 `error_page`、Content-Type 选择映射、受控 `internal` 页面 location 和页面文件。
- HTTP 块默认页面和错误页面是两个概念：默认页面用于站点默认资源；错误页面用于 4xx/5xx 状态处理。
- 错误页面编辑交互使用状态码选择器、Content-Type 选择器和单页面编辑器，不在同一屏渲染所有页面编辑器。
- 自定义状态码入口允许录入 100–599 的状态码；重复状态码或重复状态码+Content-Type 组合需要提示并阻止保存。
- Server 块未配置覆盖时继承 HTTP 块；Server 块配置空值不应破坏 HTTP 块的全局默认页面。
- 保存配置只产生草稿变更；完整发布才会经过运行时快照、原生配置物化和 Control API reload。
- 节点实例只使用自身 `NODE_*` 环境变量登记，不依赖外部注册服务或历史节点清单。
- 删除节点属于持久化资源删除操作，必须记录审计事件，并且后续启动、发布和日志流不能再把该节点视为活动目标。
- 节点 Control API 不可用时发布不应回退到 `nginx -s reload`，必须报告失败或未知状态。
- 前端页面继续使用 Vue 3、TypeScript、Ant Design Vue 和现有 fetch API 模式；HTTP 块、Server 块和错误页面共享既有中心选择及保存反馈。
- 错误页面配置的最高测试 seam 是“REST 配置 API → 原生配置预览/物化”，在该 seam 验证数据校验、继承、Content-Type 选择和生成结果，避免分别测试过多内部方法。

## Testing Decisions

- 测试只验证外部行为和生成结果，不锁定实体内部字段顺序、私有方法或具体实现细节。
- 后端 Controller 测试覆盖：
  - 合法状态码默认页面保存和读取。
  - 合法 `状态码|Content-Type` 保存和读取。
  - 非法状态码、非法 Content-Type、换行、路径穿越和超过 1MB 的内容被拒绝。
  - HTTP 块和 Server 块错误页面的继承与覆盖。
  - 重复键、空页面和未知字段的处理。
- 原生配置渲染测试覆盖：
  - 只配置状态码默认页面时生成静态 `error_page`。
  - 同时配置默认页面和 Content-Type 页面时生成 `map`、fallback 和对应页面文件。
  - `application/json; charset=utf-8` 能命中特定媒体类型规则。
  - 未匹配 Content-Type 时回退到状态码默认页面。
  - Server 覆盖不会影响其他 Server。
  - 生成文件路径只位于受控目录，且文件名不包含危险字符。
- 发布链路测试覆盖：
  - 保存草稿不会直接 reload 节点。
  - 完整发布包含运行时快照、原子物化、节点 reload 和审计记录。
  - 任一节点 Control API 不可用时返回明确的逐节点结果。
- 节点生命周期测试覆盖：
  - 节点启动后由自身调用 REST 接口登记，不启动独立注册服务。
  - 未配置 `NODE_NAME` 或控制面地址时节点跳过登记，但仍可使用本地 bootstrap 配置启动。
  - 删除节点后发布列表、日志流和 reload 目标中不再包含该节点。
- 前端测试覆盖：
  - 日志格式、安全响应头、自定义响应头卡片保持可见间距。
  - 错误页面只渲染当前选中的状态码和 Content-Type 编辑器。
  - 新增、切换、删除和保存自定义错误页面的交互反馈正确。
  - 加载旧配置时缺失错误页面字段仍能使用默认空映射，不导致页面崩溃。
- Go 模块执行 `go test ./...`、`go vet ./...` 和 Docker Compose 健康检查。原生配置预览需在 Go 实现后验证。

## Out of Scope

- 不在本 PRD 中实现完整的 WYSIWYG HTML 可视化编辑器。
- 不提供在线上传图片、字体、脚本等静态资源的错误页面资源管理。
- 不允许错误页面直接执行 Lua、Shell 或动态模板代码。
- 不将错误页面配置扩展为任意 Nginx 指令编辑器。
- 不改变已有发布三阶段流程和 Control API 硬依赖原则。
- 不通过 Redis 保存或替代错误页面配置权威数据。
- 不自动扫描节点文件反向导入错误页面配置。
- 不恢复已删除节点，也不提供基于历史名称的自动重注册策略。
- 不在本 PRD 中重新设计完整的权限、组织架构或 OAuth2 身份体系。
- 不覆盖第三方 CDN、WAF、Ingress 或云厂商专属错误页机制。

## 当前交付状态

本 PRD 记录产品需求，不作为当前实现状态的权威清单。Go 后端现状与验证边界请查阅 [`frontend-backend-migration-status.md`](frontend-backend-migration-status.md)。截至 2026-10-08，本地 Compose 已实现三固定节点的渲染、目标校验、分批发布、版本确认和回滚；PRD 中提出的通用节点登记、生产发布、安全最小权限及完整运行时契约仍未全部实现。保存配置、通过本地节点校验、发布到本地示例节点和生产环境验收是不同阶段。

## Further Notes

- 当前项目的联调 Compose 使用本地 MySQL、Redis 和 Kafka；部署环境必须确认数据库结构与控制面版本兼容。
- HTTP 请求的 Content-Type 选择实际读取 `$http_content_type`；它表示请求头 Content-Type，不是最终响应的 Content-Type。若未来需要按客户端 `Accept` 选择页面，应另行引入 `$http_accept` 维度，避免语义混淆。
- “配置已保存”“原生配置已生成”“节点已 reload”“请求实际返回正确页面”是四个不同的验证层级，界面和测试报告应分别呈现。
- 错误页面内容中如果需要 JSON，建议使用合法 JSON 文本，并由页面编辑器提供格式提示；本 PRD不强制自动格式化用户输入。
- 当前需求优先服务 HTTP 配置管理；Stream 配置不使用 HTTP `error_page` 机制。
